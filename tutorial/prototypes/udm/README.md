# UDM feasibility prototype (Part X)

A small, runnable proof that Presenton slides and Tiptap pages can share one **target-agnostic** Unified Document Model (UDM), with one adapter per module. Presenton and Tiptap are the first two adapters. A Markdown adapter and a plain-text adapter show that adding a module needs only a new adapter.

Nothing here touches the Presenton servers. The prototype reads the bundled templates in `../../../templates/*/template.json` (383 layouts) and runs everything in Node.

```bash
cd tutorial/prototypes/udm
npm ci
npm run all        # typecheck + conformance kit + 383-layout corpus + examples
```

Requires Node 22. Pinned dependencies: `@tiptap/core`, `@tiptap/pm`, `@tiptap/starter-kit`, `@tiptap/extension-table`, `@tiptap/extension-image` (all 3.30.5, the version Presenton ships), `marked` 17.0.5, and `typescript` 5.9.3 for the type check.

Measured results are in [REPORT.md](REPORT.md). That file is generated by `npm run validate`, so do not edit it by hand.

## The model

The UDM is the Part IX Artifact Spec made target-agnostic (protocol 1.3): it is not a third format. The six facets in the diagram are views over its fields:

| Facet | UDM fields |
| --- | --- |
| Content | `Block` union (heading, paragraph, list, callout, quote, divider, code, math, chart, metric, table, image, diagram, embed), `RichText` with marks bold, italic, underline, strike, code, link, math |
| Sections | `Section { id, title, role, level, summary, notes, blocks }` |
| Structure | section order, heading levels 1 to 3, nested `ListItem`, `Block.group` (same id = one visual region, such as a card) |
| Semantics | `Block.role` (subtitle, takeaway, kpi, caption, citation, label), `callout.tone`, `DataBinding` definitions, `diagramKind` |
| Media | `image { url, prompt, alt, kind, caption, assetId }`, `assets` |
| Metadata | `meta`, `provenance { origin, importedFrom }`, `language` |

Data rides in `bindings`, never inline in blocks. Imported numbers use `source.type: "static"`, and live providers keep their own source types.

**Boundary rule.** Geometry, styling and theme never enter the UDM. Anything a single target needs lives only in `ext["<adapter-id>"]`. Examples are the Presenton slot path, layout id and template id. The core never reads `ext`. An adapter writes only its own namespace, and an adapter that declares `extPassThrough` must carry every other namespace through unchanged (check C11).

## Adapter contract

```ts
interface Adapter<Native> {
  manifest: AdapterManifest;   // id (= ext namespace), blocks, marks, chartKinds, structure, features, limits, roundTrip
  serialize(udm, opts?): { native, loss, trace? };   // pure, deterministic; input already negotiated
  deserialize?(native, opts?): { udm, loss };        // required unless roundTrip == "write-only"
  validateNative(native, opts?): Issue[];            // the host's own rules
}
```

`manifest.structure.orderPreserved` is `false` for layout-driven targets. Slides place blocks in the layout's reading order, so the conformance kit compares their blocks as a multiset rather than a sequence.

## Capability negotiation (`core/negotiate.mjs`)

`negotiate` runs before every `serialize`. Its rules run in a fixed order, and each change produces a `LossEntry`. Text that leaves the document is recorded in `droppedText`, so check C3 can prove that no text is lost silently.

1. **ext**: if the target cannot carry foreign namespaces, they are dropped and the target keeps only its own.
2. **Annotations**: `notes` and `summary` are dropped when `features.notes` is false.
3. **Section titles**: if the target has no section titles, the title becomes a leading heading.
4. **Blocks**: an unsupported block follows its fallback chain until the result is supported:
   - chart -> table (from static data; title and axes become the caption) -> list -> paragraph
   - diagram -> list (or paragraph for progress and gauge)
   - table -> list -> paragraph
   - metric -> paragraph
   - list -> paragraphs
   - callout -> quote (with a bold "Note:", "Warning:" or "Success:" label) -> paragraph
   - quote -> paragraph
   - code -> paragraph with the code mark
   - math -> paragraph with the math mark
   - heading -> bold paragraph
   - image -> link paragraph
   - embed -> paragraph
   - divider -> dropped
5. **Chart kinds**: horizontal_stacked_bar -> stacked_bar -> bar; donut and polar_area -> pie; radar -> bar; scatter -> line; bubble -> scatter. When no kind is left, the block degrades by rule 4.
6. **Marks**: math -> code, and unsupported marks are dropped (a dropped link keeps its text and records the href).
7. **Nesting**: heading levels above `maxHeadingLevel` are clamped, and lists deeper than `maxListDepth` are flattened.
8. **Structure**: `group`, block `role`, section `role` and `level` are dropped when the target cannot hold them. A caption becomes a paragraph after its block when `features.captions` is false.
9. **Limits**: blocks are clipped to `maxCharsPerBlock` and sections are split at `maxBlocksPerSection`. Content is never padded.

## Conformance kit (`core/conformance.mjs`)

Each check runs on every fixture:

| Check | What it verifies |
| --- | --- |
| C0 | The manifest is valid. |
| C1 | The fixture is a valid UDM. |
| C2 | The negotiated UDM is valid and stays within the manifest. |
| C3 | Negotiation is complete: every text atom is still present or appears in a loss entry's `droppedText`. |
| C4 | Negotiation is deterministic. |
| C5 | `serialize` is deterministic and does not mutate its input. |
| C6 | `validateNative` reports no errors. |
| C7 | The loss report is well-formed. |
| C8 | The deserialized UDM is valid and neutral. |
| C9 | The round trip loses no text silently. |
| C10 | The round trip equals the negotiated input, apart from declared losses. Ids are compared when `features.ids` is set; order is compared when `orderPreserved` is set. |
| C11 | `ext` passes through and stays isolated. |

## Adapters

### `presenton.slides`

- **Native shape.** `{ templateId, slides: [{ layout_group, layout, ui, speaker_note, outline? }] }`. Here `ui` is the Template v2 tree stored in `slides.ui`.
- **Forward (`from-presenton.mjs`).** The adapter reads `ui`, which is the source of truth after edits. It skips decorative elements and vectors.
  - **Geometry.** Absolute positions are computed through components, groups and containers. Flex and grid children have no position, so their placement is approximated from the flow.
  - **Reading order.** A recursive XY-cut runs over components, and flex and grid children stay in flow order.
  - **Section title.** The largest heading that is not inside a group becomes the section title.
  - **Headings and roles.** Headings and roles are inferred from element name tokens (`title`, `heading`, `label`, `metric`, `subtitle`, and so on) and from font-size rank.
  - **Marks.** Marks are recorded as differences from the element's own font.
  - **Data.** Charts and tables become static bindings, and infographics become `diagram` blocks. Infographic-only fields go to `ext`.
  - **Notes and outline.** `speaker_note` becomes `Section.notes`, and the outline becomes `Section.summary`.
  - **Provenance.** Every block records `ext["presenton.slides"].slot`, which is the element path.
- **Reverse (`to-presenton.mjs`).** The adapter clones the layout named in `ext` (or chooses one deterministically by slot capacity) and maps blocks to slots in this order:
  1. Provenance slot.
  2. A table matched by shape, so a chart that a target turned into a table finds its chart slot again.
  3. The next free slot of the same block type, in reading order.
  4. Any compatible slot.

  An unchanged block leaves its slot byte-identical, which gives patch semantics. An edited slot is rewritten using the slot's first-run font. Slots that no block maps to are blanked so template sample data never leaks. Blocks without a slot produce `no_slot` losses.

### `tiptap` and `tiptap.basic`

`createTiptapAdapter({ extensions })` builds the schema with `getSchema(extensions)` and **derives the manifest from it**:

- **`tiptap`** (page profile) uses StarterKit, TableKit, Image, one generic `dataBlock` atom (for chart, diagram, metric, live table and embed) and the `udmAttrs` global attributes (`udmId`, `udmGroup`, `udmRole`, `udmKind`, `udmMeta`, `udmExt`).
- **`tiptap.basic`** uses plain StarterKit. Its manifest has no tables, images, data blocks, ids or `ext`, so negotiation degrades those blocks.

| UDM | tiptap.json |
| --- | --- |
| artifact title | `heading` level 1, `udmKind: "doc-title"` |
| section | boundary node: `heading` level 2 (titled) or `horizontalRule` (untitled), with `udmKind: "section"`, section id, meta and ext |
| heading 1 to 3 | `heading` 3 to 5 |
| paragraph, list, quote, code, divider | `paragraph` (a `"\n"` becomes `hardBreak`), `bulletList`/`orderedList`, `blockquote`, `codeBlock`, `horizontalRule` |
| callout | `blockquote` with `udmKind: "callout"` and the tone in `udmMeta` |
| notes | `blockquote` with `udmKind: "notes"` at the end of the section |
| table (static data) | `table > tableRow > tableHeader/tableCell > paragraph`; binding id and origin in `udmMeta` |
| chart, diagram, metric, embed, live table | `dataBlock { kind, bindingId, block, binding }`, which holds the binding definition only |
| image | `image { src, alt, title }`; kind, prompt and caption in `udmMeta` |

The validator is `schema.nodeFromJSON(doc).check()` plus a diff that catches attributes Tiptap would silently drop. The corpus run also loads every document into a headless `Editor` with `enableContentCheck: true`. Seven negative controls (known-bad documents) confirm that the validator rejects bad input. Documents without UDM attrs, as a person would write them, deserialize too: H1 and H2 start sections, a bare horizontal rule starts an untitled section, and unknown nodes degrade to paragraphs with a loss entry.

### `markdown` and `plain-text`

- **`markdown`** maps headings, paragraphs, nested lists, quotes, fenced code, GFM tables, images, `***` dividers and `---` section breaks. Marks are bold, italic and strike, plus code and links. The adapter has 181 lines. It escapes punctuation and line starts so text cannot turn into lists or headings. Where CommonMark flanking rules would reject `**`, it writes `<strong>`, `<em>` or `<del>` instead. An empty comment separates adjacent lists so they do not merge. Charts arrive already degraded to tables.
- **`plain-text`** has 33 lines and is write-only (`roundTrip: "write-only"`). It was written after `core.lock.json` was taken. The corpus run shows that no core file changed afterwards.

## Findings

See [REPORT.md](REPORT.md) for every number and its failure examples. In summary, for the 383 layouts:

- **Maps cleanly.**
  - Every content element (3,582 text, 607 images, 113 charts, 51 infographics, 35 lists, 7 tables) is represented in the UDM.
  - Every Tiptap document passes the real schema check and loads in a headless editor.
  - Presenton -> Tiptap -> Presenton returns a byte-identical `ui` for all 383 layouts.
  - With a scripted edit of every text, title, list item, table cell and chart series in `tiptap.json`, 100% of edits land in the right slot and keep the slot's base font.
  - Charts and tables keep their categories, series and cells exactly, as static bindings.
- **Needs custom Tiptap nodes.** It needs one generic `dataBlock` atom (chart, diagram, metric, live table, embed) and one global-attribute extension (`udmAttrs`). That is not one node per Presenton type: the node is target-neutral, and the UDM block type is an attribute.
- **Lossy, and reported.**
  - Per-run highlights (a second color or size inside one text element) affect 44 elements, and editing those elements flattens them to the slot's base style. A neutral `highlight` mark would close this.
  - Line breaks in titles are lost in Markdown (39).
  - Image kind and prompt are lost in Markdown.
  - Infographic visuals are not carried in Markdown or basic Tiptap; they become lists or paragraphs.
  - LaTeX becomes a code mark in Tiptap until `@tiptap/extension-mathematics` is added.
  - The corpus has no LaTeX runs and no `math` elements.
  - Most edits push text over the slot's `max_length`. Fitting text to the slot is a layout concern for the slides serializer.
- **Cannot round-trip without provenance.**
  - When `ext` is lost (Markdown, a StarterKit-only editor), the reverse direction is positional. Text-slot fidelity falls to 94.3% (Markdown) and 67.8% (basic Tiptap).
  - Almost all wrong slots (190 of 204 for Markdown, all 1,153 for basic Tiptap) are in layouts where negotiation turned a non-text block into a paragraph that then took a text slot.
  - Choosing a layout from content alone finds the original layout only 66.3% of the time (Markdown).
  - The lesson is to keep ids and `ext` in every target that can hold them (as the Tiptap page profile does). Where a target cannot, treat the doc-to-slides direction as "generate", not "patch".
- **Genericity.**
  - The core has 761 lines and names no target in code.
  - The adapters have 590 lines (Presenton), 350 (Tiptap), 181 (Markdown) and 33 (plain text).
  - While the first three adapters were built, the conformance kit and the corpus forced five target-neutral core changes:
    - a negotiation rule that drops section role and level
    - whitespace canonicalization at emphasis boundaries
    - keeping a chart's title and axes when it degrades to a table
    - `structure.orderPreserved`
    - an optional `SerializeResult.trace`
  - After the freeze, adding `plain-text` changed no core file.

## Limits

This is a feasibility prototype, not production code:

- **Not covered.**
  - Live-data tokens and the binding store.
  - Smart-mode HTML slides.
  - The Python engine side.
  - Multi-slide pagination when a long document becomes a deck. Today the adapter places one section on one slide and splits sections only by `limits`.
- **Heuristics.** Heading and role detection, flow-layout geometry and layout choice are heuristics, measured on the bundled templates only.
- **Corpus content.** The corpus uses each layout's own sample content, with no speaker notes or outlines. The fixtures cover notes and summaries instead.
